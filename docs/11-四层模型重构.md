# 11 - 四层模型重构（合作方 / 凭证 / 接入点 / 接口）

> 本章记录一次**破坏性重构**：把"连接器"这一个概念拆成四层，并把密钥从"连接"里摘出去。
> 决策口径来自产品讨论（「连接器不要带鉴权相关的功能，它的作用就是配置合作方管理的接口」），
> 迁移方式是**全部推倒重来**，不留双写、不留宽限期。

## 0. 结论先行

| 之前 | 之后 |
|---|---|
| `connector`（连接器）：地址 + 公共头 + 超时 + 重试 + **一套密钥** | `endpoint`（接入点）：地址 + 公共头 + 超时 + 重试，**没有密钥** |
| `connector_auth`（1:1 挂在连接器上） | `partner_credential`（1:N 挂在合作方下，可多套、可设默认） |
| 无 | `partner`（合作方）：商业主体、状态、合同、联系人 |
| `connector_operation` | `endpoint_operation`（+`credential_mode` / `credential_id`） |

四层职责一句话：

- **合作方**：哪家公司、现在能不能用（停用会级联）、合同号、联系人、优先级。不放 URL，不放密钥。
- **凭证**：一套密钥 + 类型 + 生效期。一个合作方可以有多条，其中一条是默认。
- **接入点**：一个合作方下的一组接口的公共配置（baseUrl / 公共头 / 超时 / 重试 / 限流）。
- **接口**：方法、路径、出入参契约、前后置脚本、单接口超时覆盖，以及**用哪条凭证**。

一句话记住分界：**换地址不动密钥，换密钥不动地址。**

## 1. 为什么这么拆

原来的 `connector` 同时承担两件事：**连接事实**（域名、头、超时）和**商务/凭证事实**（密钥、授权）。
两者变化节奏完全不同——换地址是技术动作，换密钥是商务/安全动作。绑在一起导致：

1. 同一家供应商两套凭证（新旧并存、查询与回传分开授权）只能建两个"连接器"，
   于是同一家公司在系统里出现两次，env、超时、公共头各维护一份，日志统计被拆开；
2. 单个接口需要不同凭证（或干脆不需要）时没有位置表达，只能把密钥写进 `operation.headers`——那是明文；
3. 停用一家公司要逐个停它下面的连接器，"禁用"这个语义无处安放；
4. 密钥加密、脱敏、token 缓存都只能按"连接器"分组，而业务上的分组单位其实是"合作方"。

## 2. 表结构

迁移脚本：`V6__partner_endpoint.sql`（建表）→ `V7__migrate_connector_to_partner_endpoint.sql`（搬数据）
→ `V8__drop_connector_tables.sql`（删旧表）。三步分开是为了**任一步失败都能停下来看**，
而不是一个大脚本跑到一半留个半成品库。

### 2.1 partner

```sql
CREATE TABLE partner (
  id            BIGINT PRIMARY KEY,
  code          VARCHAR(64)  NOT NULL,          -- 全局唯一，编排与日志引用它
  name          VARCHAR(128) NOT NULL,
  status        TINYINT      NOT NULL DEFAULT 0, -- 0草稿 1正常 2停用 3禁用
  contact_name  VARCHAR(64),
  contact_phone VARCHAR(32),
  contract_no   VARCHAR(128),
  priority      INT          NOT NULL DEFAULT 100, -- 数字越小越优先
  remark        VARCHAR(512),
  created_at, updated_at, deleted
);
```

`status` 四态的差别是刻意的：**停用**是可恢复的业务暂停，**禁用**是风控拉黑（页面上文案不同，
禁用不给一键恢复的入口）。两者对调用的效果一样：整家公司的接口立刻不可调用。

### 2.2 partner_credential

```sql
CREATE TABLE partner_credential (
  id             BIGINT PRIMARY KEY,
  partner_id     BIGINT       NOT NULL,
  code           VARCHAR(64)  NOT NULL,          -- 合作方内唯一
  name           VARCHAR(128) NOT NULL,
  type           VARCHAR(32)  NOT NULL,          -- header|script（V9 起；旧六型已迁移/停用）
  config         JSON         NOT NULL,          -- 密钥位置 ENC:v1: 密文
  is_default     TINYINT      NOT NULL DEFAULT 0,
  status         TINYINT      NOT NULL DEFAULT 1,
  effective_from DATETIME,                       -- 生效期，换密钥可以提前录、到点自动启用
  effective_to   DATETIME,
  remark         VARCHAR(512),
  created_at, updated_at, deleted,
  UNIQUE KEY uk_cred_partner_code (partner_id, code)
);
```

敏感字段（加密）与非敏感字段（明文，便于排障）的分界：

| type | config 形状 | 加密字段 | 明文保留 |
|---|---|---|---|
| `header` | `{"headers":[{"name":"X-Api-Key","value":"…","in":"header"}]}` | 每条 `headers[].value` | `name`、`in` |
| `script` | `{"script":"…groovy…","secrets":{…},"ttlSeconds":3600,"sensitiveKeys":["Authorization"]}` | `secrets.*` 的每个值 | `script` 正文、`ttlSeconds`、`sensitiveKeys` |

**为什么从六型收敛成两型**（2026-10-29，迁移脚本 `V9__credential_two_types.sql`）：

原来的 `api_key / basic / bearer / oauth2_cc / login_token` 是「按见过的主流供应商枚举」。
现实中供应商的鉴权往往是这些模式的变体：两个头组合、签名放在 header、先查一次鉴权码再带上来、
签名串要拼 timestamp + nonce + body 再 HMAC。每遇到一种就要加一个 `type` 并改解析器——
平台变成在追着供应商改。收敛后：

- **能静态列出来的**（「就是在请求里加这两个头」）→ `header`，配几条就几条；
- **要算出来的**（签名、换 token、多步）→ `script`，用代码描述，平台不再增长 `type`。

迁移时 `api_key` 无损转成 `header`（`name/value/in` 三个字段正好对上）；
`basic / bearer / oauth2_cc / login_token` 需要 base64 或换 token，SQL 层面转不了（密码是密文），
一律置为停用并在备注写明「请改写为 header 或 script」——比起悄悄转出一个错的凭证，停用更难被忽略。

### 2.3 endpoint

```sql
CREATE TABLE endpoint (
  id             BIGINT PRIMARY KEY,
  partner_id     BIGINT       NOT NULL,
  code           VARCHAR(64)  NOT NULL,   -- 全局唯一；编排 DSL 里的 connector 字段存的就是它
  name           VARCHAR(128) NOT NULL,
  category       VARCHAR(64),
  base_url       VARCHAR(512) NOT NULL,
  default_headers JSON,
  timeout_ms     INT DEFAULT 10000,
  retry          JSON,
  credential_id  BIGINT,                  -- 可空：本接入点默认用哪条凭证
  status         TINYINT NOT NULL DEFAULT 0,
  remark         VARCHAR(512),
  created_at, updated_at, deleted,
  UNIQUE KEY uk_endpoint_code (code),
  KEY idx_endpoint_partner (partner_id)
);
```

### 2.4 endpoint_operation

在原 `connector_operation` 基础上加两列（**列名仍保留 `connector_id`**，见 §5 的取舍）：

```sql
credential_mode VARCHAR(16) NOT NULL DEFAULT 'INHERIT',  -- INHERIT | OVERRIDE | NONE
credential_id   BIGINT
```

### 2.5 invoke_log

```sql
ALTER TABLE invoke_log
  ADD COLUMN partner_id           BIGINT,
  ADD COLUMN partner_credential_id BIGINT,
  ADD COLUMN credential_type      VARCHAR(32);
```

这三个字段是**对账的前提**：没有它们，运营只能看到"某个接入点失败了"，
说不出"是哪家合作方、用的哪套密钥、当时是不是正在换 key"。

## 3. 凭证解析链

```
接口 credential_mode
 ├─ NONE      → 不鉴权（哪怕接入点/合作方配了凭证）
 ├─ OVERRIDE  → 用接口上的 credential_id（必须属于同一合作方）
 └─ INHERIT   → 接入点 credential_id
                └─ 空 → 合作方 is_default=1 且 status=1 且在生效期内的那条
                        └─ 空 → 不鉴权
```

三个约定：

1. **解析不到不算错误**。很多三方接口本来就不鉴权，"没配凭证"必须能正常跑。
2. **归属校验在保存时做，启停校验在调用时做**。保存时校验凭证是否属于本合作方
   （防止把 A 家的 key 用到 B 家的接入点上）；停用/过期这类状态变化随时可能发生，
   只能在调用那一刻判。
3. **缓存 key 是 `credentialId:type`**，不是 `partnerId`。一条合作方两套凭证各自换 token，
   按合作方做 key 会互相污染——这是从 1:1 走到 1:N 时最容易踩的坑。

## 4. 校验顺序与错误码

调用一次接口，状态校验顺序是 **合作方 → 接入点 → 接口**：

| 顺序 | 判据 | 错误码 | 对外文案 |
|---|---|---|---|
| 1 | `partner.status != 1` | `PARTNER_DISABLED`(403) | 合作方已停用：<名称> |
| 2 | `endpoint.status != 1` | `ENDPOINT_DISABLED`(403) | 接入点已停用：<code> |
| 3 | `operation.status != 1` | `OPERATION_DISABLED`(403) | 接口已停用：<code> |

顺序刻意是这样：反过来的话，人会对着"接口已停用"去改接口，而真正的原因是那家公司被拉黑了。
网关侧（`GwErrorCode`）把这三个都映射成 `APP_FORBIDDEN`——对调用方来说都是"这个入口现在用不了"，
没必要让它去猜平台内部的层级。

## 5. 关键取舍

### 5.1 Java 类名与列名不改

`Connector` / `ConnectorOperation` / `IConnectorService` 这几个名字**保留**，`connector_id` 列名也保留。
理由不是懒：`connectorId` 在 flow / gateway / invokelog 三个模块里有 100+ 处引用，
改名会把这些全部拖进来，而收益只是"读起来顺一点"。实际改动只有两处：

- `@TableName("connector")` → `@TableName("endpoint")`，`@TableName("connector_operation")` → `@TableName("endpoint_operation")`
- REST 路径 `/api/connectors/**` → `/api/endpoints/**`

于是编排链路（DSL 里 `connector` 字段、`flow_step_run.connector_id`）**零改动**。
文档与界面上统一叫"接入点"，代码里看到 `Connector` 就知道是历史包袱。

### 5.2 脚本作用域名仍叫 `auth`

Groovy 前置脚本里 `ctx.auth` 是公开的书写约定，线上已有脚本在用。这次只换了解析来源
（合作方凭证 → 明文配置注入 `ctx.auth`），**作用域名没动**。改名会让已有脚本静默读到空值。

### 5.3 复制接入点不带凭证

`copy` 复制接入点与接口，凭证沿用同一个（`credential_id` 原样带过去），但**不会**复制出一条新凭证。
复制一份密钥出来，等于多了一个没人负责轮换的副本。

## 7. 前端

菜单「数据接入」变成三层递进，正好对应从商务到技术的三步：

```
数据接入
├─ 合作方      /partners                      ← 新增
│   └─ 凭证    /partners/:partnerId/credentials  （showLink:false）
├─ 接入点      /endpoints                     ← 原 /connectors
├─ 数据源服务接口 /services
├─ ETL 处理器  /etl-handlers
├─ 环境与密钥  /envs
└─ 调用方应用  /apps
```

- 合作方列表：状态用下拉改（停用/禁用前把"会连带多少接入点、多少接口失效"念给用户听）。
- 凭证页：按类型动态渲染字段，密钥永远显示 `******`，提交时带 `******` 视为"不修改"。
  「自检」按钮只打 `tokenUrl` / `loginUrl`，不碰业务地址，把"配置错了"和"三方坏了"分开。
- 接入点列表：去掉了鉴权列，改成「凭证」列——显示它最终会用哪一条（空 = 合作方默认）。
- 接口详情第 4 步是「凭证」：继承 / 指定 / 不鉴权三选一。
- 调用明细加「合作方」「凭证」两列。
- 画布节点属性面板的接入点下拉按合作方分组（`el-option-group`）。

```bash
# 编译

```

迁移正确性的自检项（手工）：

1. `SELECT COUNT(*) FROM partner` = 原 `connector` 行数（`deleted=0` 的部分）；
2. `SELECT COUNT(*) FROM endpoint` 同样一致，且 `partner_id = id`；
3. 每个有 `connector_auth` 的连接器，对应合作方下有一条 `is_default=1` 的凭证，`config` 密文与原来逐字节一致；
4. `endpoint_operation.credential_mode` 全为 `INHERIT`；
5. 任取一条旧流程，`connector` 字段的 code 仍能在 `endpoint` 里查到 → 发布/试跑不报"接入点不存在"。

## 9. 已知未做

- **mTLS / 证书**：两种凭证都不管证书，要做得先加证书存储。
- **出向请求签名**（`sign = HMAC(secret, method+path+timestamp+body)`）：签名输入需要最终 body，
  而凭证解析发生在渲染之前，位置不对。`script` 型能覆盖「直接用 secret 算签名」的场景（用 `utils.hmacSha256`），
  但算不了「对最终 body 的摘要」——那需要真正把签名提到 `buildSpec` 之后、`execute` 之前。
- **接入点级限流**：表里没有 `rate_limit` 列（原计划有），入向限流仍在网关的 `GwRateLimiter`。
- **合作方合并/拆分**：目前只能手工重建。

## 10. script 型凭证的脚本契约

```groovy
// 可读：ctx.secrets（已解密的密钥）、ctx.credentialId、ctx.http、utils、log(...)
// 可写：ctx.headers、ctx.queryParams、ctx.ttlSeconds

def resp = ctx.http.postForm('https://api.example.com/oauth/token', null, [
    grant_type: 'client_credentials',
    client_id: ctx.secrets.clientId,
    client_secret: ctx.secrets.clientSecret
])
if (resp.status != 200) { throw new IllegalStateException('换 token 失败：HTTP ' + resp.status) }
ctx.headers['Authorization'] = 'Bearer ' + resp.json.access_token
ctx.ttlSeconds = 3600
```

| 变量 | 说明 |
|---|---|
| `ctx.secrets` | 配置里 `secrets` 解密的键值，密钥不进脚本正文（便于单独轮换） |
| `ctx.http.get(url, headers)` / `.postForm(url, headers, form)` / `.postJson(url, headers, body)` | 返回 `{status, body, json, error}`；**非 2xx 不抛异常**，由脚本决定怎么处理；超时写死 3s/10s |
| `utils` | `json`、`jsonParse`、`jsonpath`、`md5`、`sha256`、`hmacSha256`、`base64`、`urlEncode` |
| `ctx.ttlSeconds` | > 0 才缓存结果（按 `credentialId:script` 分段，带单飞）；不设则每次调用都现算 |

三条边界：

1. **沙箱墙钟仍是 3s**（`GroovySandboxOptions.DEFAULT_TIMEOUT_MS`），所以「脚本里换 token」的三方往返必须快于 3s；
   慢接口的正解是把 token 缓存起来（`ctx.ttlSeconds`），而不是把超时改大。
2. **没声明 `sensitiveKeys` 时，脚本产出的所有 header / query 都打码**——宁可多遮也不能漏。
3. 脚本写错（语法/抛异常）统一包成 `AUTH_FAILED "凭证脚本执行失败：…"`，自检面板会原样显示这句话，
   不会变成「接口返回 500」。
